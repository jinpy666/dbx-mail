# 版本部署变更说明 v0.1.5

- 版本：`0.1.5`（`manifest.json` / `package.json` / `backend/Cargo.toml` 三处一致）
- 产物：`com.mjj3610.mail-0.1.5-<target>.dbxp`，共 5 个平台
  （`windows-x64` / `linux-x64` / `linux-arm64` / `darwin-x64` / `darwin-arm64`）
- 变更性质：**打包与发布链路变更**，无功能变更、无数据结构变更、无接口变更
- 影响范围：`.github/workflows/plugin-release.yml`（新增）、`scripts/package.mjs`（目标名映射）、
  版本号三处、README 安装说明

## 1. 为什么需要这个版本

v0.1.4 只发布了 `windows-x64` 一个包。原因是硬限制而不是疏忽：

```
$ dbx-plugin package --target linux-x64
Native plugin target 'linux-x64' does not match build host 'windows-x64'
```

Sidecar 是预编译的 Rust 二进制，官方 CLI 拒绝跨平台打包，本机（Windows/GNU 工具链）
无论如何也产出不了 macOS / Linux 的二进制。唯一可行路径是**在目标平台自己的 runner 上编译**。

## 2. 做法：调用官方复用工作流

新增 `.github/workflows/plugin-release.yml`，`on: release: types: [published]` +
`workflow_dispatch`（可对已有 tag 重跑），调用
`t8y2/dbx/.github/workflows/plugin-release-reusable.yml@main`：

| 输入 | 值 | 原因 |
| --- | --- | --- |
| `package-command` | 见下 | 自建打包，不用官方 CLI |
| `package-path` | `dist/*.dbxp` | 复用工作流的默认值是 `dist/*.dbxp`，保持一致 |
| `metadata-path` | `dist/*.artifact.json` | 同上 |
| `install-plugin-cli` | `false` | 打包由 `scripts/package.mjs` 完成，不需要 CLI |
| `go-version` | `''` | 无 Go 后端，跳过 setup-go |
| `rust-toolchain` | `stable` | 需要 cargo |
| `build-matrix` | 5 个 `runner`/`target` 对 | 默认矩阵就是这 5 个，这里显式写出便于增删 |

`package-command` 的实际执行序列：

```bash
# Linux：keyring 的 sync-secret-service 后端要链接 libdbus
sudo apt-get install -y --no-install-recommends libdbus-1-dev pkg-config
npm ci
npm run build                      # vite → ui/（单文件 bundle）
export RUSTUP_TOOLCHAIN=stable     # 关键，见下
( cd backend && cargo build --release --locked )
node scripts/package.mjs --output-dir dist
```

### 2.1 必须覆盖 `RUSTUP_TOOLCHAIN`

`backend/rust-toolchain.toml` 固定了 `stable-x86_64-pc-windows-gnu`（本机没有 MSVC Build Tools，
且 MSVC 的 `link.exe` 常被 Git 自带的 `link` 抢占）。这个 toolchain 名只在 Windows 宿主上合法，
macOS / Linux runner 读到会去装一个不存在的工具链而失败。`RUSTUP_TOOLCHAIN` 环境变量的优先级
高于 `rust-toolchain.toml`，所以 CI 里统一覆盖成 `stable`（各平台宿主默认工具链）。

### 2.2 目标名映射修正

`scripts/package.mjs` 里 `platformTarget()` 原先把 macOS 映射成 `macos-x64` / `macos-arm64`，
与商店、CI 矩阵使用的 `darwin-x64` / `darwin-arm64` 不一致。这些名字会直接进
包内 `manifest.json` 的 `entrypoints.backend.executable`（`bin/<target>/backend`），
名字对不上宿主就找不到 sidecar，因此已改为 `darwin-*`。

## 3. 产物与校验

CI 的 publish 阶段会做这些校验（任一不过就整体失败），均已满足：

- 每个 `.artifact.json` 的 `sha256` / `size` 必须与同目录 `.dbxp` 的实际字节一致；
- 包内不得含 `signature.json`（候选必须未签名）；
- 5 个 target 的包内 `manifest.json` 身份（id / name / description / publisher / version / permissions）必须完全一致；
- target 不得重复，且必须匹配 `^[a-z0-9-]{1,64}$`。

产物旁边会多出一份 `release-candidates.json`（`plugin` 身份 + 5 条 `artifacts`），
商店候选由它生成，不手抄 sha256。

## 4. 平台运行前提

| 平台 | 前提 |
| --- | --- |
| Windows | 无额外依赖（Microsoft 凭据管理器走系统 API） |
| macOS | 优先 Keychain；二进制**未做代码签名与公证**，个别环境下首次运行可能被 Gatekeeper 拦下（可执行 `xattr -d com.apple.quarantine <binary>` 放行） |
| Linux | 凭据库走 Secret Service（需要桌面环境的 keyring 守护进程 + `libdbus`）；没有可用凭据库时自动退化为 AES-256-GCM 本地加密文件（`secrets.key` + `secrets.bin`，权限 0600） |

## 5. 发版步骤

```bash
# 1) 版本号已改好，本地冒烟
npm run build
( cd backend && cargo build --release )
node scripts/package.mjs --output-dir dist     # 只产出当前平台，仅用于验证脚本

# 2) 提交 + 打 tag
git push origin main
git tag v0.1.5 && git push origin v0.1.5

# 3) 建 Release 并 **Publish**（draft 不触发 release: published，CI 不出包）
#    正文用本文件

# 4) 等 5 个 build + 1 个 publish 全绿，然后取候选清单
#    Release 资产里会出现 5 个 .dbxp + release-candidates.json
```

## 6. 已知遗留

- **不做 universal 包**：带原生 sidecar 的插件无法合并成 universal。
- **arm64 Windows 缺失**：`windows-11-arm` runner 不在官方默认矩阵内，`windows-arm64` 本次未出包；
  如后续需要，在 `build-matrix` 里加一项 `{"runner":"windows-11-arm","target":"windows-arm64"}` 即可。
- **CI 产物与本地产物字节不同**：工具链、压缩实现、时间戳都会影响，所以商店候选的
  `sha256` / `size` 只能取 CI 那份 `release-candidates.json`，不能用本地 `dist/` 的数字顶替。
